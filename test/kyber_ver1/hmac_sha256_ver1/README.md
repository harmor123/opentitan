# 测试说明

## 一.hmac sha3-256

### 1. 环境与指令集约束 (重要警告)

本汇编器**非标准 GNU RISC-V 汇编器**，大量基础指令被禁用，代码中已使用特殊技巧绕过：
* **禁用指令**：`j`, `bgt`, `blt`, `sltu`, `lbu`, `sb`, `LOOP`
* **替代方案**：
  * 无 `lbu/sb` (单字节操作) -> 使用 `lw` 按字加载 + `andi` 掩码过滤垃圾字节。
  * 无 `bgt/sltu` (大于比较) -> 使用 `addi` 相减 + `srli` 提取符号位判断溢出。
  * 仅支持 `LOOPI 循环次数, 循环体内指令条数` 进行固定次数循环。
* **寄存器别名映射**：`x` 寄存器与 `w` 寄存器物理同源。修改 `x4` 会改变 `w0` 的低 32 位；调用 `keccakf` 破坏 `w28-w31` 等同于破坏 `x28-x31`。
* **内存对齐**：对于 `bn.lid/sid` 指令，数据指针**必须 32 字节对齐** (`.balign 32`)，否则会引发硬件异常或数据错乱。
---
### 2. API 接口规范
#### 2.1 函数调用
```assembly
jal x1, hmac
```
#### 2.2 输入参数 (调用前需设置)
| 寄存器                                                       | 描述                       | 约束                |
| :----------------------------------------------------------- | :------------------------- | :------------------ |
| `x10`                                                        | 指向 KEY 数据的指针        | 无需 32 字节对齐    |
| `x11`                                                        | KEY 的长度 (字节数)        | `> 0`               |
| `x12`                                                        | 指向 Message 数据的指针    | 无需 32 字节对齐    |
| `x13`                                                        | Message 的长度 (字节数)    | `>= 0`              |
| `x14`                                                        | 指向输出 HMAC 哈希值的指针 | 建议至少 4 字节对齐 |
| *注：函数内部会在栈上分配 64 字节空间保存现场（`ra`, `x10-x14`），调用者需保证栈指针 `sp` 正常。* |                            |                     |
#### 2.3 输出结果
* 函数执行完毕后，32 字节的 HMAC-SHA3-256 结果将被写入 `x14` 指向的内存中。
#### 2.4 内部依赖函数
`hmac` 函数会依次调用以下外部函数（需由链接脚本提供）：
* `sha3_init(x10=context, x11=32)`
* `sha3_update(x10=context, x11=data_ptr, x12=data_len)`
* `sha3_final(x10=context, x11=output_ptr)`
---
### 3. 大小端序 说明
**本架构为严格的小端序。** 这在编写测试数据时极其容易出错，必须遵循以下规则：
#### 3.1 字符串/字节数组的内存排布
如果你想输入字符串 `"Hi There"`（对应十六进制 `48 69 20 54 68 65 72 65`）：
* **低地址放低字节**。
* 在汇编中使用 `.word` 倒序拼接：
```assembly
my_message:
    .word 0x54206948    /* 对应 "Hi T" (0x48, 0x69, 0x20, 0x54) */
    .word 0x65726568    /* 对应 "here" (0x68, 0x65, 0x72, 0x65) */
```
#### 3.2 哈希输出结果的比对
假设 SHA3-256 算出的标准理论值（大端人类可读格式）为：
`a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a`
在 DMEM 内存（小端序）中，它的实际存储形态将是倒序的 8 个 32 位字：
```assembly
/* 小端序存储期望值 */
    .word 0x4a43f880   /* 对应最后 4 字节: 4a 80 f8 43 倒序 */
    .word 0x4b0ad880   /* ... */
    .word 0x82fa49b4
    .word 0x43de4f58
    .word 0x62d661a0
    .word 0x5647c151
    .word 0x66d71ebf
    .word 0xf8c6ffa7   /* 对应前 4 字节: a7 ff c6 f8 倒序 */
```


### 4. 测试代码内存布局说明
在 `.data` 段中，必须严格按照以下结构和大小端对齐分配变量：
```assembly
.data
/* 1. 栈空间：必须 32 字节对齐 */
.balign 32
stack:
  .zero 1024
stack_end:
/* 2. SHA3 上下文：存放内部状态，大小视具体 sha3 实现而定 (此例为 212 字节) */
.balign 32
context:
  .zero 212
/* 3. Keccak 轮常数：极其关键！由于 keccakf 使用 bn.lid x31, 0(x6++) 读取，*/
/*    指针每次自增 32 字节，所以每个 .dword 常数必须强行用 .balign 32 填充！ */
.balign 32
rc:
.balign 32
  .dword 0x0000000000000001
.balign 32
  .dword 0x0000000000008082
  /* ... 共 24 个轮常数，每个前面都要加 .balign 32 ... */
/* 4. HMAC 辅助缓冲区 */
.balign 32
inner_hash:    /* 存放内部哈希 H(ipad || msg) 的结果，固定 32 字节 */
  .zero 32
.balign 32
key_buf:       /* 当 KEY > 136 字节时，作为 H(KEY) 的临时中转站 */
  .zero 200    /* 分配 200 字节留足余量，防止 BN 指令越界读脏数据 */
.balign 32
ipad:          /* ipad 缓冲区，实际使用 136 字节 */
  .zero 200
.balign 32
opad:          /* opad 缓冲区，实际使用 136 字节 */
  .zero 200
```
---
### 5. 如何修改测试用例
#### 场景 A：测试超长 KEY (例如 160 字节全 0x0b)
1. 在 `main` 中修改长度寄存器：
   ```assembly
   li      x11, 160         /* 必须改这里！ */
   ```
2. 在 `.data` 中铺满对应长度的数据（注意小端序 `.word` 排列）：
   ```assembly
   my_key:
       .rept 40             /* 160 / 4 = 40 个 word */
       .word 0x0b0b0b0b
       .endr
   ```
#### 场景 B：测试空消息
1. 准备一个 dummy 指针（可以指向任意地址，因为长度为 0 不会发生实际读取）：
   ```assembly
   la      x12, my_key      /* 随便复用个地址即可 */
   li      x13, 0           /* 核心是长度设为 0 */
   ```
#### 场景 C：更换消息内容
假设要输入 `"abc"` (`0x61 0x62 0x63`)：
```assembly
.balign 4
my_message:
    .word 0x00636261        /* 'a'=61, 'b'=62, 'c'=63, 第四字节补 0 */
/* 对应 main 中： */
/* li      x13, 3           */
```

## 二.hkdf

#### 2. API接口规范
##### 2.1 函数调用
```assembly
jal x1, hkdf_expand
```
##### 2.2 输入参数 (调用前需设置)
| 寄存器 | 描述                          | 约束                                      |
| :----- | :---------------------------- | :---------------------------------------- |
| `x10`  | 指向 PRK (伪随机密钥) 的指针  | **必须恰好为 32 字节** (SHA3-256输出长度) |
| `x11`  | 指向 Info (上下文信息) 的指针 | 无需 32 字节对齐，可为 `b''` (空)         |
| `x12`  | Info 的长度 (字节数)          | `>= 0`，最大 255                          |
| `x13`  | 期望输出的总长度 L (字节数)   | `> 0`，最大 `255 * 32 = 8160`             |
| `x14`  | 指向输出 OKM 的指针           | 建议至少 4 字节对齐，空间 >= L            |
##### 2.3 输出结果
* 函数执行完毕后，长度为 `L` 字节的派生密钥将被写入 `x14` 指向的内存中。
---
#### 3. 大小端序 说明
**本架构为严格的小端序。** 这在填充 `info` 数据时极易出错：
##### 3.1 Info 字符串的内存排布
假设要传入 Info = `"f0 f1 f2"`（3字节）：
* **低地址放低字节**。
* 在汇编中使用 `.word` 倒序拼接，且高位补 `0x00`：
```assembly
.balign 4
my_info:
    .word 0x00f2f1f0    /* 对应 0xf0, 0xf1, 0xf2, 0x00(无效位) */
```
* 此时 `x12` 必须设为 `3`，汇编内的尾部掩码逻辑会自动把最后一个 `0x00` 剔除，**绝不会多算一个字节**。
##### 3.2 最终输出 OKM 的比对
输出结果在 DMEM 中是以小端序按字存储的。如果你的 Python 脚本输出了大端的 OKM：
`039e7b28e10a2d20...`
在内存/二进制文件中的实际排列（以 4 字节为单位倒序）：
```assembly
/* 对应前4字节 03 9e 7b 28 的实际存储 */
    .word 0x287b9e03
/* 对应接下来 4字节 e1 0a 2d 20 的实际存储 */
    .word 0x202d0ae1
```
#### 4. 测试代码内存布局说明
由于防冲突机制，HKDF 测试代码对 `.data` 段的命名和空间要求极其严格：
```assembly
.data
/* 1. 栈空间 */
.balign 32
stack:
  .zero 1024
/* 2. SHA3 内部依赖 (必须存在且命名不可改) */
.balign 32
context:     .zero 212
rc:          ... (24个轮常数，需 .balign 32 填充)
inner_hash:  .zero 32
key_buf:     .zero 200
ipad:        .zero 200
opad:        .zero 200
/* ==========================================
 * 3. HKDF 专属隔离区 (极其关键！)
 * ========================================== */
/* 消息拼接区：T_prev(32) + info(最大255) + counter(1) = 288 */
.balign 32
.globl hkdf_msg_buf    /* 绝对不能叫 msg_buf！ */
hkdf_msg_buf:
  .zero 320            /* 预留大一点，防止 BN 指令越界读脏数据 */
/* 状态安全屋：存放 N, i, offset 等 */
.balign 32
.globl hkdf_ctx
hkdf_ctx:
  .zero 64             /* sha3 绝对不会碰这个区域 */
/* 单次 HMAC 结果暂存 */
.balign 32
.globl t_buf
t_buf:
  .zero 32
```
---
#### 5. 如何修改测试用例
##### 场景 A：测试空 Info (`info = b""`)
如果你的协议不需要上下文（如之前提到的混合密钥例子中 `info=b""`）：
1. 随便指向一个地址（因为长度为 0 不会发生实际读取）：
   ```assembly
   la      x11, hkdf_ctx     /* 随便复用个地址即可 */
   li      x12, 0            /* 核心：info_len = 0 */
   ```
2. 此时第一轮的 `msg` 实际上只有 1 个字节 `0x01`，第二轮有 33 个字节（`T(1)` + `0x02`）。
##### 场景 B：测试只输出 32 字节 (`L = 32`)
1. 修改 `x13`：
   ```assembly
   li      x13, 32
   ```
2. 内部只会执行 1 次循环（`N=1`），不会发生 `T_prev` 的拷贝，逻辑走最简路径。
##### 场景 C：测试长 Info (如 20 字节字符串)
假设 Info = `"Hybrid key exchange"` (20 字节)：
```assembly
.balign 4
my_info:
    .word 0x6b207962    /* "by k" 倒序 */
    .word 0x20646948    /* "Hid " 倒序 */
    .word 0x79616863    /* "chay" 倒序 */
    .word 0x63617078    /* "xpac" 倒序 */
    .word 0x00656e67    /* "gne\0" 倒序 */
/* 对应 main 中： */
/* la      x11, my_info */
/* li      x12, 20 */
```
*(注：20 字节不是 4 的整数倍，代码里的 `copy_info_tail` 会自动用 `andi` 掩掉最后一个字的最高字节 `0x00`，精准传入 20 字节，无需手动垫位！)*
